# OpenBlue R12: Topology diagram & static consistency review

## Mission
Make R8–R11 planning information understandable without creating false evidence of a live network. R12 reconciles the current read-only in-memory proposal documents into a deterministic network **concept graph**.

### Inputs (read-only)
- R8 detected network drop inventory and tentative room classification.
- R10 rack geometry anchors, patch panels and port-to-drop assignments, with review states.
- R11 conceptual switches and explicitly proposed switch-to-panel/switch-to-switch links.
- Existing R9 pathway review states as already propagated through the R10 analysis.

### Graph contract
- Derived `openblue.topology-review/1`; generated by pure `buildTopologyDiagram`, with stable string IDs incorporating source record identifiers.
- Node classes: `rack`, `switch`, `panel`, `drop`.
- Edge classes: `placement` means rack containment ONLY; `logical` means an R11 operator-proposed link; `allocation` means an R10 patch-port-to-drop proposal. None is physical connectivity evidence.
- No phantom endpoints: if referenced panel or drop is missing, suppress that edge and add `EDGE_ENDPOINT_MISSING` to review findings. Do not silently repair the relationship.
- Findings include stale or missing rack anchors, conflicting U positions, logical connection errors, missing patch panels, untraced R9 paths (informational), and room unassigned drops (informational).
- Static, no credentials, no SNMP/LLDP, no ICMP pings, no switches queried, no remote fetches.
- Each derived node is clickable and keyboard focusable for inspection; the graph offers all/review/connected-proposal filters.
- Render at most 28 nodes per class (112 nodes). Surface truncation visibly; full counts, findings and export remain complete.
- Explicit download of `*.topology-review.json` review snapshot. No new persisted sidecar or changes to `openblueprint.project/1`, EVIE `openblueprint.evie-proposal/1`, room notes, pathways, racks or logical topology.

## Fail-closed policy
- Graph nodes only exist when corresponding records are present in currently loaded data.
- Stale R10/R11 references yield warnings and may suppress drawn edges. A drawn edge always means proposal, never **installed**, **up**, **reachable**, **tested**, **qualified**, **certified** or **approved**.
- Placement edges cannot be treated as inferred cables. Proposed 2D path status cannot establish signal viability or permission to drill.

## Test plan
1. Create representative two-drop plan, rack, panel and logical switch with link. Verify correct node/edge types and all counts.
2. Delete patch panel: no invented panel node, missing edge warning and logical-link consistency issue.
3. Move rack anchor: static stale issue persists and switch requires review. Remove a drop from R8 inventory: no phantom node and an issue for missing edge.
4. An R10 allocation with no R9 waypoint plan gets an informational warning, not a false installed status.
5. Empty plan has no inferred network nodes. Snapshot is stable, explicitly proposal-only, with no credentials or execution.
6. CI `npm ci`, `npm test`, `npm run build`. Browser smoke: filter changes, focus node by mouse/keyboard, selected-node descriptions, expanded issues, scroll cap, JSON download. Verify no mutation of sidecars or EVIE flow.
